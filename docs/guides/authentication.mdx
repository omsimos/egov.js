# Configure credentials safely

## Choose a constructor

**Explicit clients** accept credentials either in `create(...)` or in a token or
authentication method, depending on the service. They work with any secret
manager and are appropriate when credentials come from a vault, platform
binding, or request-scoped provider.

```ts
import { eMessageApi } from "egov.js/eMessage";

const client = eMessageApi.create({
  accessToken: await secrets.get("EMESSAGE_ACCESS_TOKEN"),
  baseUrl: "https://ws-message.e.gov.ph",
});
```

**Environment-backed clients** use `fromEnv(...)` and fail fast when a required
value is missing. You can pass a custom environment object for runtimes without
Node's `process.env`.

```ts
const client = eMessageApi.fromEnv({
  baseUrl: "https://ws-message.e.gov.ph",
  env: { EMESSAGE_ACCESS_TOKEN: platform.env.EMESSAGE_ACCESS_TOKEN },
});
```

<Warning>
  Never expose **partner secrets, API keys, or access tokens** in browser code, public logs,
  screenshots, issue reports, or client-visible error payloads.
</Warning>

## Handle token exchanges

**eGov AI, eGov SSO, eReport, and eVerify** exchange a long-lived partner
credential or one-time code for a shorter-lived token. Store that token only as
long as its workflow requires and honor expiry metadata when the service returns
it. The eGov SSO token response does not expose an expiry field.

**eGov SSO exchange codes** should be treated as single-use values. Perform the
exchange and citizen-profile request on the server, then issue your own secure
application session.

## Separate hosts from secrets

**Every `fromEnv(...)` call still requires `baseUrl`**. Keeping the host explicit
lets deployment configuration distinguish sandbox, staging, and production
without overloading the credential lookup.

See the [service overview](../services/overview.mdx) for every credential name.
